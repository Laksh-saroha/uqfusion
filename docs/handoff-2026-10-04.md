## 2. The queue: how to run it, and what to know

Everything lives in `runs/vis_benchmark_stride4_ep25_ext/` (gitignored).
* **Monitor:** the dashboard on http://localhost:8771, or `queue.log`, `progress.csv`, `live.json`.
* **Pause/resume:** write `control.json` with `{"paused": true}` or `false`, or use the dashboard.
  A pause takes effect after the current epoch's checkpoint. Resuming re-runs the data gate
  (~5–7 min) and keeps patience intact.
* **Launch or relaunch, always detached via WMI.** Processes started with `Start-Process` died when
  the Claude desktop app auto-updated (2026-09-30 04:55Z). Use:
  ```powershell
  $si = New-CimInstance -ClassName Win32_ProcessStartup -ClientOnly -Property @{ShowWindow=[uint16]0}
  Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine="cmd.exe /c A:\Uncertain\runs\vis_benchmark_stride4_ep25_ext\run_queue.cmd"; CurrentDirectory='A:\Uncertain'; ProcessStartupInformation=$si}
  ```
  `run_dashboard.cmd` starts the dashboard the same way. A killed run resumes from its own `last.pt`.
  Use the system Python 3.13 (GPU torch), **never `.venv`** (CPU torch).
* **The laptop must stay on and awake.** The queue survives app updates but not a reboot, sleep or
  power-off. A Start-menu power-off on 2026-10-02 at 19:43Z cost ~9 h, because nothing relaunched
  the queue until the next morning.
* **ETA:** 25 runs left, at least ~89 h. Expect it to finish around **Oct 8–10**. The minutes per
  epoch are tracking the estimate (yolo12m 11.7 vs 12.0, yolo26l 12.4 vs 12.2). The yolo26 family is
  the likeliest to run long: yolo26l_seed0 trained 23 extension epochs where 13 was the minimum.
* **Settled, don't re-open:**
  - Two concurrent runs on the GPU is a null: 5.03 vs 5.07 it/s (+0.8%). They also race on the labels
    `.cache` file.
  - Epochs 1–3 of every run are slow because of the Ultralytics warm-up. That is not a regression.
  - The Lenovo Custom power mode is already at its limits.
* **Recipe deviations** (authorized 2026-09-27):
  - The batch size is planned per family to fit the 12 GB card: yolo12m, yolo26l, yolo11l and
    yolov10b at 8, yolo12x at 4.
  - nbs=64 is kept, so the effective batch stays 64.

## 3. Table 1 at patience 20 (partial)

```
python scripts/bench_ext_table.py      # -> runs/vis_benchmark_stride4_ep25_ext/table1_ext.md + table1_ext_runs.csv
```

**How runs are scored and checked:**
- Each run is scored at its best mAP50-95 epoch over base + extension, keeping the earliest
  maximum, i.e. the checkpoint EarlyStopping keeps.
- Only families with every seed finished are ranked.
- All 68 rows were cross-checked against `progress.csv` and the server's progress file, and every
  one agrees.
- `yolo12x_seed0`'s `results.csv` lacks extension epoch 22. Its stop is exactly best + 20, so the
  missing row holds no new best. The table notes this.

**Readings so far** (provisional until the l/x families finish):
* yolo26m leads at **0.2626 ± 0.0109**, ahead of yolo26s at 0.2502 ± 0.0090. The gap (0.0124) is
  larger than both seed sds. With n = 3 per family this is a screen, not a test.
* **Patience barely reorders the field.** Spearman ρ = 0.954 against the ep25 ranking, and only 16 of
  68 runs beat their ep25 best.
* **The exception is yolo26n, 16th → 8th** (+0.0276, all 3 seeds improved, best near epoch 63).
  Truncating at 25 epochs penalised it specifically.
* **The leader may change:** yolo26l_seed0 alone scores 0.2733.

These are training-time val logs on `data_vis_stride4.yaml`, restored labels (`8ed69b5974ed`). The
val split spans pohang00–04, so no new scoring event happened and no ledger entry is needed. The
table is not a holdout claim.
