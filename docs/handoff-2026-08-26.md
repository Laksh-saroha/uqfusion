## 4. Uncommitted work on `fusion-uq-phase3`

165 insertions across three files, plus untracked launchers. All of it is live —
the running queues are using it — and **none of it is committed**. The branch
also has **no remote at all** (`no upstream configured`), so nothing is pushed
anywhere.

- **`scripts/run_queue.py`** — adds `ir_benchmark_queue()` (the §3 matrix), and
  changes divergence policy: a diverged run no longer pauses the whole queue, it
  is marked `diverged` and the runner walks on. The old behaviour let one noisy
  epoch on an independent run halt 92 others overnight. The `_ft` safety this
  used to provide is already covered independently by `cmd_run`'s parent guard,
  which refuses to start any stage whose parent is not `done`.
- **`scripts/watch_divergence.py`** — the mAP backstop now needs **two
  consecutive** crashed epochs (`map_confirm`, default 2), each judged against
  the best known *at that row*. `ir_bench_yolov8n_seed0` tripped the old
  single-epoch backstop while all three train losses improved monotonically —
  one bad validation pass, not decay.
- **`src/uqfusion/uq/train_gaussian.py`** — adds `_is_resumable_checkpoint()`.
  Ultralytics strips `epoch`/`optimizer` on any `trainer.stop`, so a
  divergence-stopped checkpoint *looks* resumable and is not.
- **Untracked:** `ir_benchmark_run{,_detached}.cmd`,
  `ir_benchmark_dashboard{,_detached}.cmd` — resume-safe launchers, pinned to
  the `config.yaml` `gpu_python` interpreter (not PATH `python`, which is the
  CPU-torch venv).

Also untracked and **not** worth committing: `Test_1/`, `scratch_val_perclass*`.

## 6. Traps worth remembering

- Server `run_queue.py` deliberately has **no** in-process divergence alarm; the
  sidecar watcher (PID 23650) covers it. Don't "fix" that.
- A divergence-stopped checkpoint cannot be resumed — `--redo` restarts from
  epoch 0. Only a `PauseRequested` exit is resumable.
- `runs/queue_vis_server/runner.log` is **stale**; the live one is
  `runner-20260825.log`. Prefer `state.json` for status.
- `state.json`'s `runs` dict only contains runs that have *started* — a pending
  count taken from it is meaningless. Count against `queue.json`.
- On the server, `javascript_tool` has a hard 30 s cap. Anything longer must be
  fired into a file and polled from a **second** terminal.
